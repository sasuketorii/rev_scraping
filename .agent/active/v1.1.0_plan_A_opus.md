## 0. Executive design summary

v1.0.0-dev shipped the complete *feature* surface (spider, cf-evaluate, relocate, auth, doctor, vpn, captcha, MCP × 15 tools). What is still missing for **GA** is **operational maturity**: portable Linux build, real-run CI matrix, verified hotfix behaviour, distribution hygiene (license/audit, troubleshooting docs), and a small number of late-cycle CLI inconsistencies (notably `auth login --allow-no-vpn`).

The plan partitions remaining work into **MUST** (6 items — production blockers), **SHOULD** (7 items — high-value polish), and **DEFER** (6 items, all reserved for v1.2+). Strategy:

1. **Stabilise** the existing surface (re-verify hotfix-2, plug Phase-7c residual gap, ship `--allow-no-vpn`) before adding any new capability.
2. **Make CI deterministic** by splitting `#[ignore]` E2E into "deterministic-mock" (always run) and "live" (manual dispatch).
3. **Prove Linux parity** under Ubuntu 22.04 in CI matrix and via Docker — gating GA.
4. **Document for distribution** (CHANGELOG, CONTRIBUTING, SECURITY, troubleshooting).
5. Defer all paid / external-account-bound work (residential proxies, brew tap, signing, monitoring) to v1.2+.

Wall-day estimate: **~14 wall-days serial; ~7 wall-days with 3-engineer parallel; ~5 wall-days with 4-engineer parallel.** No new workspace crate is strictly required; one optional helper crate (`stealth-measure`) is proposed for the SHOULD-tier `measure` subcommand.

Highest-risk item: **B5 — Linux build/test green.** Mitigation: invest M1 entirely in containerised reproduction before any other Linux-touching sub-phase begins.

## A. Scope partition (MUST / SHOULD / DEFER)

MUST = a missing or unverified item that would cause a reasonable downstream user (engineer joining team, agent in production, paying customer) to file a P0/P1 bug within the first week. SHOULD = strongly desirable polish that elevates from "works" to "feels finished". DEFER = either paid-account-bound, requires a release infrastructure we have not built yet, or is large enough to warrant its own minor release.

### MUST (6) — GA blockers

## B. MUST items — design detail

### B1. Phase 9-hotfix-2 re-verification (Chrome dialog suppression)

**Problem.** Hotfix-2 added flags to chromiumoxide launch (`--no-default-browser-check`, `--disable-features=…`) to suppress the "Chrome wants to open a new window" / "Set as default browser" modal dialogs on macOS during `auth login`. Whether the flags survive (a) Chrome version drift since then and (b) headed launch under modern macOS 14/15 is unverified.

**Design.**
1. Add an `auth doctor` sub-command (or extend top-level `doctor`) that:
   - Launches Chrome headed via the same code path as `auth login`, navigates to `about:blank`, waits 2s, evaluates `chrome.runtime` presence as proxy for "no dialog stole focus", screenshots window, exits.
   - Emits a deterministic JSON envelope: `{ chrome_version, profile_dir, flags_applied[], dialog_detected: false|true|"unknown" }`.
2. Add an `#[ignore]`-by-default integration test `auth_login_no_dialog_macos` gated by `REV_AUTH_RUN_HEADED_E2E=1` (env already used by hotfix-1 follow-ups item 4) that:
   - Spawns `rev-auth login --mode probe --profile _ci`, asserts exit 0 within 10s, asserts no `displayDialogs` artefact in profile dir.
3. Add a release-time **manual checklist item** in `docs/release-checklist.md`: human visually confirms "no dialog appeared" on macOS 14 and macOS 15.

**Acceptance.**
- `cargo test -- --ignored auth_login_no_dialog_macos` green on macOS-14 CI runner.
- `auth doctor` returns `dialog_detected: false`.

**Effort.** 0.5 wall-day. 🟡 medium.

### B2. `auth login --allow-no-vpn` / `--require-vpn`

**Problem.** `spider` and `cf-evaluate` accept `--allow-no-vpn`; `auth login` does not, despite enforcing the same VPN-required policy under the hood. Inconsistency surface.

**Design.**
- Reuse the shared `VpnRequirementFlags` arg-group already used by `spider`. Currently `auth login` constructs its own VPN probe; refactor to consume the shared flags struct (no new logic — only argument plumbing).
- `--require-vpn` mirrors the spider semantics (overrides `policy.toml` if it says `false`).
- `--allow-no-vpn` mirrors spider semantics: bypass the probe, but the audit log must record `vpn_skipped_reason: "user_flag --allow-no-vpn"`.
- Document in README §6 (auth) and §8 (CLI consistency table). No new config keys.

**Acceptance.**
- `rev-stealth auth login --help` lists both flags.
- Unit test: invoking with `--allow-no-vpn` while `policy.toml` requires VPN succeeds and audit-log entry contains the skipped-reason.

**Effort.** 0.25 wall-day. 🟡 medium.

### B3. `spider --use-auth` member-only E2E

**Problem.** The Phase 9 deliverable claim is "cookies captured at login transparently authorise downstream `spider`". Empirically validated on login itself; never validated on a downstream protected fetch.

**Design.**
1. Pick a low-cost, low-risk test target. Three candidates, in preference order:
   - **(preferred)** A self-hosted test fixture: a tiny axum server serving `/login` (form) + `/members/only` (200 only if a known cookie present, 401 otherwise) launched as a `cargo test` fixture. Deterministic, no external dependency.
   - **(secondary)** `brain-market.com` — already used for spider validation; member tier exists.
   - **(tertiary)** `DaiGo` — already used for auth login (6 cookies captured).
2. Add an integration test `spider_use_auth_authorised_member_fetch`:
   - `#[ignore]` by default. Gated by `REV_E2E_LIVE_AUTH=1` for fixtures (a, b, c). The axum-fixture variant should NOT require the gate — it is deterministic.
3. Test flow: provision a `_e2e_member` auth profile (pre-encrypted blob committed under `tests/fixtures/auth/` with a CI-only key), run `spider --use-auth=_e2e_member --url <protected>`, assert status 200 + body contains a known canary string only present for logged-in users.

**Acceptance.**
- Fixture-server variant runs deterministically in CI on every PR.
- Live-site variants pass on manual-dispatch CI.

**Effort.** 1.5 wall-days. 🔴 high (fixture engineering + cookie encryption key handling in CI).

### B4. CI deterministic green

**Problem.** Workflow YAML exists (5 jobs: test-unit, test-clippy, build-obscura, test-obscura-lifecycle, test-cdp-shim-lifecycle, test-spider-fallback). Two jobs are `continue-on-error: true` (cdp-shim, spider-fallback). PR cycle never verified.

**Design.**
1. **Remove `continue-on-error`** from `test-cdp-shim-lifecycle` and `test-spider-fallback` jobs. Either the test is deterministic enough to be required, or it belongs in a manual-dispatch workflow. Move flaky ones to `.github/workflows/e2e-manual.yml` triggered by `workflow_dispatch`.
2. **Pin toolchain** via `rust-toolchain.toml` (`channel = "stable"`, `components = ["rustfmt", "clippy"]`) so `dtolnay/rust-toolchain@stable` resolves identically across runs.
3. **Add `cargo fmt --check`** job (currently missing).
4. **Add `cargo deny check`** job using `EmbarkStudios/cargo-deny-action@v1`. Requires writing `deny.toml` (see §J).
5. **Add `cargo audit`** as a weekly cron workflow (`schedule: cron: "0 0 * * 1"`), not on every PR (would block on advisories beyond our control).
6. **Capture per-job timing** to `actions/upload-artifact` JSON for trend monitoring.

**Acceptance.**
- 5 consecutive successful PR runs (any docs PR) with all jobs green.
- One intentional failing-test PR demonstrates red status (gate works).

**Effort.** 1 wall-day. 🟡 medium.

### B5. Linux build/test green

**Problem.** macOS-only verified. Linux is the production target for most agent deployments.

**Design.**
1. **Local Docker repro first.** Provide `docker/linux-ci/Dockerfile` (Ubuntu 22.04 base, installs: build-essential, pkg-config, libssl-dev, libsecret-1-dev, ca-certificates, chromium-browser, xvfb). `docker/linux-ci/run.sh` mounts the workspace and runs `cargo test --workspace --no-fail-fast`.
2. **CI matrix.** Promote `test-unit` and `test-clippy` to a matrix:
   ```yaml
   strategy:
     matrix:
       os: [ubuntu-22.04, macos-14]
   ```
   Allow both to run in parallel.
3. **Platform conditional code.** Audit for hard-coded macOS paths:
   - `~/Library/Application Support/...` → use `directories` crate / XDG fallback already mostly in place (Phase 9 chose `~/.config/`).
   - macOS Keychain (`security-framework`) → already abstracted through `keyring` crate v3, which on Linux uses Secret Service (libsecret) — needs runtime presence check + fallback to passphrase mode.
   - Chrome path discovery: probe `chromium-browser`, `google-chrome`, `google-chrome-stable`, `chromium`, `ungoogled-chromium` in that order on Linux; on macOS keep `/Applications/Google Chrome.app/...`.
4. **Headed-browser CI on Linux** is impractical; run headed-Chrome tests under `xvfb-run` in the Docker image. Mark non-CI tests `#[cfg(not(target_os = "linux"))]` if they require visible focus.
5. **File-perm portability.** Confirm `0600` / `0700` writes (auth profiles) work on Linux ext4 + on tmpfs; add a unit test in `stealth-auth` that asserts perms after atomic write.

**Acceptance.**
- `docker/linux-ci/run.sh` exits 0 on a clean checkout.
- Matrix job `test-unit (ubuntu-22.04)` green.
- Matrix job `test-clippy (ubuntu-22.04)` green.

**Effort.** 2.5 wall-days. 🔴 high (most uncertainty; Chrome on headless Linux can surface unknowns).

### B6. Obscura cookie-injection E2E

**Problem.** Phase 9c specified `Network.setCookies` over the obscura `cdp_shim`. The path compiles and unit-tests pass against a fake CDP server. Whether the **real obscura binary** correctly applies cookies and renders a member page is unverified.

**Design.**
1. New integration test `obscura_cookie_injection_member_page`:
   - Reuses the axum fixture-server from B3 (or the brain-market profile).
   - Launches obscura via `obscura-bridge`, injects cookies through `cdp_shim::set_cookies`, navigates to `/members/only`, asserts response body.
   - `#[ignore]` gated by `REV_SCRAPING_RUN_OBSCURA=1`.
2. Add this test to the existing `test-obscura-lifecycle` CI job (already builds & caches obscura) — adds one extra `cargo test … -- --ignored obscura_cookie_injection_member_page`.

**Acceptance.**
- New `#[ignore]` test passes locally with `REV_SCRAPING_RUN_OBSCURA=1` on macOS.
- Same test passes in CI under Ubuntu 22.04 (depends on B5 readiness).

**Effort.** 1 wall-day. 🔴 high (obscura cookie behaviour might require small `cdp_shim` patch).

**Effort.** 0.25 wall-day. 🟡 medium.

### C2. `NavResult.http_status` wiring

Today `NavResult.http_status: Option<u16>` is always `None`. Plumb it from the obscura `cdp_shim` `Network.responseReceived` event:

1. In `obscura-bridge::cdp_shim`, subscribe to `Network.responseReceived`. Capture `response.status` for the **main-frame** navigation only (skip subresources).
2. Surface as `MainFrameNavigationStatus` in the `NavResult` builder.
3. Backward-compat: keep `Option<u16>` — `None` is legitimate when obscura backend is bypassed (reqwest path) or before navigation completes.
4. Add a doc note on `chromiumoxide`-system-Chrome path: same mechanism (already mostly wired); merge to one shared helper.

**Effort.** 0.5 wall-day. 🟡 medium.

### C3. `vpn_rotation_events` JSON schema

Author `docs/json-schemas/vpn_rotation_events.schema.json` (JSON Schema draft-2020-12). Required top-level fields: `event_id`, `ts` (RFC 3339), `kind` (enum: `rotate_request`|`rotate_success`|`rotate_failure`|`leak_detected`|`stickiness_violation`), `country`, `from_ip_masked`, `to_ip_masked`, `proxy_profile`, `reason`. Document in README §12 + the schema file.

Also add a `examples/` directory next to the schema with one JSON sample per `kind` value. Add a CI step that validates examples against schema (`ajv` via npx, or `jsonschema` Python — pick a CI-friendly tool; `taplo` is for TOML, not applicable).

**Effort.** 0.5 wall-day. 🟡 medium.

### C4. Cookie auto-refresh warning

Add to `auth status`:
- For each cookie in each profile, compute `days_until_expiry = (expires_unix - now) / 86400`.
- If `days_until_expiry < threshold` (default 7, configurable via `policy.toml` `[auth] cookie_expiry_warn_days = 7`), emit a warning row: `WARN  profile=work scope=app.example.com cookie=session expires in 5 days`.
- Exit code stays 0 (advisory). Add `--fail-on-near-expiry` to flip to exit 2.
- Surface the same warning through MCP `auth_status` tool response (`warnings: []` array).
- No auto-refresh logic — out of scope, both v1.0.0-dev and v1.1.0.

**Effort.** 0.5 wall-day. 🟡 medium.

### C5. `measure` subcommand (Phase 8e)

Reserved for a tiny new crate **`stealth-measure`** (optional, behind feature flag `measure`) to keep the workspace clean. Provides:

```
rev-stealth measure --url https://abrahamjuliot.github.io/creepjs/ \
                    --backend obscura --vpn jp \
                    --out results/<ts>.json
```

The subcommand navigates the URL with chosen backend, waits for a settle hook (page-specific JS condition: `creepjs` exposes `window.creep` after ~3s; `bot.sannysoft.com` table renders after ~2s; `pixelscan.net` exposes a JSON endpoint), extracts the result (textContent of known selectors), normalises to a `MeasureResult` envelope, writes JSON.

Built-in target presets (`--target creepjs|sannysoft|pixelscan|bot-detector`) with per-preset settle selectors. Custom targets via `--selector <css> --wait <ms>`.

**Effort.** 1.5 wall-days. 🟡 medium.

### C6. `doctor` stack expansion

Extend `doctor` (or add `doctor --deep`):
- **obscura:** `obscura --version`, vendored-binary existence, hash match against expected.
- **VPN:** parse `policy.toml`, list configured providers, ping endpoints, check IP leak baseline.
- **sites recipe:** scan `~/.config/rev_scraping/recipes/`, validate each TOML schema, warn on missing field.
- **auth profile:** list profiles, decrypt+re-encrypt loopback (proves key in keyring still works), summarise cookie expiry.
- Output: human table + `--json` envelope.

**Effort.** 1 wall-day. 🟡 medium.

### C7. README §15+ + CHANGELOG + CONTRIBUTING + SECURITY

- README §15 *Troubleshooting*: top 10 failure modes with fix recipe (VPN not connected, Chrome path missing, keyring locked on Linux, obscura version drift, recipe TOML syntax, AUP not allowed, …).

### F.2 Caching strategy

- **Workspace cargo cache:** `Swatinem/rust-cache@v2` with `shared-key: workspace-${{ matrix.os }}` to avoid cross-OS pollution.
- **obscura cache:** keyed by `vendor/obscura` git rev (already implemented; preserve).
- **chromium cache (Linux):** install via apt with `actions/cache` on `/var/cache/apt`.

### F.3 Secrets

- `SURFSHARK_USER` / `SURFSHARK_PASS` for live VPN tests → only in `e2e-manual.yml` repository env, NOT in `ci.yml`. Confirm with branch-protection that no PR from a fork can read them (default behaviour: forks cannot, but document explicitly).
- `AUTH_FIXTURE_KEY` (32-byte hex, encrypts the `tests/fixtures/auth/_e2e_member.jar.enc` committed blob). Used by B3 fixture-server test in `ci.yml`.
- Never set `RUST_BACKTRACE` to a value that leaks env contents.

### F.4 Coverage (optional, SHOULD-tier)

Optional `cargo-llvm-cov` job that uploads to Codecov. Defer unless team wants the badge — Codecov has rate-limit risk on private/large workflows. **Recommend defer** to v1.1.1 or later.

## J. Security hardening

### J.1 `cargo-deny`

Author `deny.toml`:
- `[licenses]`: allow `MIT`, `Apache-2.0`, `BSD-3-Clause`, `BSD-2-Clause`, `ISC`, `MPL-2.0` (review case-by-case), `Unicode-DFS-2016`, `0BSD`. Confidence threshold 0.93.
- `[bans]`: deny `openssl` (we want `rustls`-only). Deny `git2` unless feature-justified.
- `[advisories]`: `vulnerability = "deny"`, `unmaintained = "warn"`, `yanked = "deny"`.
- `[sources]`: only `https://github.com/rust-lang/crates.io-index`. Allow specific git sources for `obscura` and `wreq` if vendored.
