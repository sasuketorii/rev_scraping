## 0. Executive design summary (synthesis)

Both plans agree on the macro shape:

1. v1.2.0 is an **additive productionisation release**, not a stealth-engine rewrite.
2. Backward-compatibility is the single hardest constraint (v1.1.0 configs & MCP clients must keep working).
3. Four workstreams (VPS / Hermes / Config / Agentability) map to one Phase-10 DAG with three parallel lanes.
4. stdio JSON-RPC is the **only** MCP transport in v1.2.0. TCP/WS/HTTP gateways are deferred to v1.3.
5. ≥ 600 PASS test target.
6. systemd `LoadCredentialEncrypted=` is the preferred secret-injection path.

They diverge meaningfully on:

- **Crate layout:** Plan A keeps zero new mandatory crates (additive modules only); Plan B introduces two new crates (`stealth-config`, `stealth-agent-contracts`).
- **`deny_unknown_fields` rollout:** Plan A hard from v1.2.0 + `REV_SCRAPING_CONFIG_LENIENT=1` escape hatch; Plan B strict-only-for-new-parser + `--compat-v1` mode.
- **`schema_version`:** Plan A bumps to `1` (no migration shipped); Plan B bumps directly to `2` (with an actual migration).
- **ErrorEnvelope shape:** Plan A `kind` (rust enum), Plan B `code` (snake_case enum tag). Same idea, different field names.
- **outputSchema source-of-truth:** Plan A `docs/json-schemas/*.json` + `include_str!`; Plan B `schemars`-generated from Rust types at build time.
- **Test-count distribution:** Plan A ~149 net add (≥608 total); Plan B ~230 net add (≥689 total).
- **Timeline:** Plan A 24 engineer-days / 10 wall-days; Plan B 12-14 calendar days with risk to 20.

The synthesis below selects per-section on **technical merit, not author identity**.

## B. VPS productionisation

### B.1 `rev-auth --headless` flag

**Plan A:** Tri-state enum `{Headed, Headless, Xvfb}` resolved from CLI > env > `auto`. `auto` picks headless on Linux-no-DISPLAY, headed on macOS, xvfb if `xvfb-run` present + `--remote-display`. Macros guard against accidental macOS default flip.

**Plan B:** Quad-state enum `{Auto, Headed, Headless, Xvfb}` with separate boolean `--headless` / `--xvfb` flags as shortcuts. Resolution table is identical to Plan A's.

**統合判断:** Adopt **Plan B's quad-state enum** (more explicit; matches `clap::ValueEnum` idiom) **with Plan A's `auto`-resolution table** (Plan A's table is more rigorous about macOS default preservation). Adopt Plan A's regression guard (`cfg!(target_os="macos")` compile-time check). Env var name: `REV_AUTH_DISPLAY` (Plan B) is more descriptive than `REV_AUTH_HEADLESS` (Plan A); keep `REV_AUTH_HEADLESS=1` as alias per Plan B's deprecation table.

### B.2 Local-capture → VPS export (zero-code track)

Both plans agree: **`scp -p ~/.config/rev_scraping/auth/<P>.enc vps:...`** is the primary path. Plan A keeps it minimal; Plan B adds explicit `install -d -m 0700` first and `.meta.json` companion file. **統合判断:** Adopt Plan B's more explicit commands.

### B.3 systemd unit templates

**Plan A:** 5 files (system-scope only): `rev-scraping-vpn.service`, `rev-scraping-mcp.socket`, `rev-scraping-mcp@.service` (per-connection), `rev-scraping-soak.timer/.service`. Hardening directives table.

**Plan B:** 6 files split by scope: `dist/systemd/system/` (3 files) + `dist/systemd/user/` (3 files including `rev-auth-vnc@.service` Xvfb). No per-connection instantiation; `Accept=no` socket-activated single process.

**統合判断:** Adopt **Plan B's system+user split layout** (operators in non-root VPS environments need user-scope; Plan A's omission is a real gap). Adopt **Plan B's `Accept=no`** (single long-lived MCP server is correct for stdio NDJSON state — Plan A's `Accept=yes` per-connection model would fork on every request and lose session state). Adopt **Plan A's `rev-scraping-soak.timer`** for daily `doctor --vps` health (Plan B omits this; it's cheap and high-value).

> **Debate trace:**
> - Plan A: `Accept=yes` per-connection.
> - Plan B: `Accept=no` single-process.
> - **統合判断: Plan B wins.** Per-connection forking would break `session_id` correlation and lose in-process token-bucket state across MCP calls. Plan A's choice was a sound systemd idiom but a wrong fit for a stateful stdio-JSON-RPC server.

### B.4 `LoadCredentialEncrypted=` integration

**Plan A:** Prefers native read of `$CREDENTIALS_DIRECTORY/auth-pass` (30-line stealth-auth change); env fallback retained.

**Plan B:** Uses `LoadCredentialEncrypted=auth-passphrase:...` + `Environment=REV_SCRAPING_AUTH_PASSPHRASE_FILE=%d/auth-passphrase` — i.e. **file path** in env, content read from file.

**統合判断:** **Plan B's pattern wins.** Reading the credential from a path (not from an env-var that's visible to `systemctl show`) raises the security floor and matches systemd ≥ 252 idiom exactly. Plan A's "native read of `$CREDENTIALS_DIRECTORY`" is the same idea but Plan B's `..._FILE` env-var pattern is the canonical systemd recipe and requires *zero* rev-auth code changes (only a 5-line keystore.rs addition that reads `$REV_SCRAPING_AUTH_PASSPHRASE_FILE` if set). Document env-only fallback for distros < systemd 252.

### B.5 `doctor --vps`

Both plans list nearly identical checks. **統合判断:** Take Plan A's bullet list (LUKS / gluetun / DISPLAY / keyring / .env perms / systemd active) and Plan B's failure-mode table (each check has explicit "fails when" semantics). Output: JSON default + human formatter.

## D. Config UX

### D.1 `config` subcommand surface

**Plan A:** 9 subcommands: show, validate, init, paths, diff, history, rollback, migrate, profile, gc.

**Plan B:** 12 subcommands: init, show, doctor, set, get, validate, migrate, path, edit, diff, history, rollback.

### D.2 `deny_unknown_fields` + `schema_version`

**Plan A:** All Policy/AuthorizedFile/SiteRecipe structs gain `deny_unknown_fields`; `schema_version = 1` field added (default via `serde(default)` to keep v1.1 fixtures parsing); `REV_SCRAPING_CONFIG_LENIENT=1` escape hatch.

**Plan B:** Same `deny_unknown_fields` but jumps **directly to `schema_version = 2`** with a real migration; `--compat-v1` flag as escape hatch.

**統合判断: Plan A wins on schema_version, Plan B wins on escape mechanism.**

- **schema_version = 1** (not 2): Plan A is right — there is no breaking change in v1.2.0, so jumping to `2` is semantically wrong and forces users to run `migrate` for cosmetic reasons. Reserve `= 1` now; first real migration becomes `1 → 2` in (likely) v1.3.
- **Escape hatch:** Plan B's `--compat-v1` per-invocation flag is safer than Plan A's `REV_SCRAPING_CONFIG_LENIENT=1` env var because it's audit-loggable and scoped to a single call. Adopt **both**: env for systemd convenience, flag for ad-hoc operator use.

> **Debate trace (deny_unknown_fields rollout):**
> - Plan A: hard from v1.2.0, env escape, removed in v1.3.
> - Plan B: hard for v2 schema, `--compat-v1` for v1 files indefinitely.
> - **統合判断: hybrid.** Adopt hard `deny_unknown_fields` from v1.2.0 **for all structs** (Plan A's vigour), with `schema_version = 1` keeping v1.1 fixtures fully parsable (no unknown fields means no impact), **and** both `REV_SCRAPING_CONFIG_LENIENT=1` env + `--compat-v1` flag as escape hatches (Plan B's safety net). Remove escape hatches in v1.4 (deferred from Plan A's v1.3 — gives more grace).

### D.3 Profiles

Both plans: `--profile <name>` global flag. Plan A picks `~/.rev_scraping/profiles/<name>/` (nested); Plan B keeps profiles minimal in v1.2.0 (`--profile` only, full management v1.3).

**統合判断:** Adopt **Plan A's nested path** (`~/.rev_scraping/profiles/<name>/`) and **Plan A's full profile subcommand suite** (`profile list/create/switch/delete`) — config UX score of 90+ is harder to reach without first-class profile commands.

### D.4 MCP config tools

Plan A: 6 tools (policy_show, policy_propose_change, policy_apply_change, aup_add_target, aup_remove_target, config_validate). Plan B: 4 tools (config_show, config_validate, config_path, config_diff).

**統合判断:** Adopt **Plan A's 6-tool surface** — `policy_propose_change`/`apply_change` capability handshake is a security feature Plan B is missing (agents should never write directly; they propose, the operator approves via `proposal_id` from a previous call). Add Plan B's `config_path` (cheap and useful) for **7 tools total**.

### D.5 Backup / diff / rollback

Plan A: `atomic_write_with_backup`, sha256-skip, `.bak.<epoch_ms>` (millis), gc keep=5. Plan B: `ConfigWriter` trait + `BackupRecord` + `audit_write`, `.bak.<epoch>` (ISO timestamp like `20260520T141500Z`).

**統合判断:** Adopt **Plan B's trait-based `ConfigWriter`** (testable seam) + **Plan A's sha256-skip optimisation** (prevents needless backup spam) + **Plan A's `.bak.<epoch_ms>` numeric millis** (sortable lex order; Plan B's ISO is also sortable but is harder to parse mechanically). gc keep=5 from Plan A.

## E. Agentability

### E.1 outputSchema source of truth

**Plan A:** `docs/json-schemas/{tool}.{input,output}.json` files; `include_str!` into `stealth-mcp::tools.rs`. Single PR diff reviewable; CI strict-mode validator validates the same files.

**Plan B:** `schemars` crate generates JSON Schema from Rust types at build time; `cargo run -p stealth-mcp --bin dump-tool-schemas > tools.json` then `jq` check. Schema is a *function* of the Rust struct.

**統合判断: Plan A wins.** Reasons (technical):

1. **Strict-mode lint visibility.** OpenAI Agent SDK strict mode rejects schemas that `schemars` happily generates (notably: `schemars` emits `nullable` differently from draft-07, and per-field `description` requires `#[doc]` discipline). Hand-curated JSON files are inspectable in PR diff; generated ones change opaquely.
2. **`outputSchema` ≠ Rust response shape 1:1.** Output schemas often need `examples`, `enum`, `format`, and field-level `description` text that does not naturally live in a Rust struct. Forcing it into `#[schemars(...)]` attrs bloats the type system.
3. **One source for both Rust and the agent.** Agents (Hermes/HermesAgent/Claude) consume the JSON; the Rust server merely echoes it. The JSON should *be* the source.

**Compromise:** Adopt Plan B's `dump-tool-schemas` binary as a **CI assertion** — it loads the `include_str!`-baked schemas and dumps them; CI validates them against draft-07 + OpenAI strict subset (separate lint passes per Plan B's risk row).

### E.2 ErrorEnvelope

**Plan A:** `{kind, message, retryable, retry_after_ms, hint, schema_ref, correlation_id}`; field name `kind`; closed Rust enum.

**Plan B:** `{code, message, retriable, hint, retry_after_ms, schema_ref, doc_url}`; field name `code`; closed Rust enum w/ `#[serde(rename_all="snake_case")]`.

**統合判断:** Field name `code` (Plan B) — convention across Anthropic/OpenAI/MCP error shapes. `retriable` (Plan B's spelling) — Stripe/AWS convention. Add **`correlation_id`** (Plan A) and **`doc_url`** (Plan B) — both are agent-load-bearing. **Closed enum** (both agree). Final:

```rust
pub struct ErrorEnvelope {
    pub code: ErrorCode,        // closed snake_case enum
    pub message: String,
    pub retriable: bool,
    pub hint: String,           // REQUIRED, one actionable sentence (Plan B: required; Plan A: optional). Plan B wins — agents need it.
    pub retry_after_ms: Option<u64>,
    pub schema_ref: Option<String>,
    pub correlation_id: Option<String>,
    pub doc_url: Option<String>,
}
```

ErrorCode variants: union of both plans' enums (Plan A: 25 variants; Plan B: 21 variants). Final 26 variants (super-set; resolves overlaps by picking the more specific name, e.g. `RelocateAmbiguous` not `Ambiguous`).

Embedded in BOTH `result.error` (success-shape) and JSON-RPC `error.data`. Both plans agree.

> **Debate trace:**
> - Plan A: `kind`, `retryable`, `hint` optional.
> - Plan B: `code`, `retriable`, `hint` required.
> - **統合判断: Plan B wins on field names + required hint** (agent ergonomics: an always-present hint string is more valuable than the alternative). Plan A wins on the variant inventory (more exhaustive). Merge.

### E.3 Rate-limit runtime

**Plan A:** Per-host token bucket in `crates/stealth-core/src/rate_limit.rs`. Config priority: CLI > recipe > defaults. Honour `Retry-After` w/ ±20% jitter.

**Plan B:** Per-tool token bucket in new `stealth-mcp/src/rate_limit.rs` module + `ToolRateLimit { capacity, refill_per_second, key_fields }` advertised in tool definition.

**統合判断: Both, layered.** They are not in conflict — they address different layers:

- **Per-host bucket** (Plan A): enforces target-server rate respect (the SiteRecipe contract). Lives in `stealth-core`, applies to both `spider` (CDP) and `fallback_http` (reqwest).
- **Per-tool bucket** (Plan B): enforces MCP-caller rate respect (an agent calling `recipe_propose_endpoint` 1000×/sec). Lives in `stealth-mcp`.

Both are token buckets; both honour `Retry-After`. Rate-limit *advertisement* via `ToolRateLimit` in the tool definition (Plan B) is preserved so agents can self-regulate. Default for **per-tool**: enabled (Plan B's D9). Default for **per-host** when no recipe says so: pass-through (Plan A's D9) — backward compat with v1.1.

### E.4 Idempotency keys

Plan A: dedupe key `(domain, purpose, path, http_method)` for `recipe_propose_endpoint`; sha256 for `recipe_import`; per-profile fcntl lock for `auth_login_start`. Plan B: dedupe `by purpose+path+method` (similar) with `dedupe=false` CLI escape.

**統合判断:** Plan A's recipe key adds `domain` (correct — recipes are domain-scoped). Plan B's `dedupe=false` CLI escape valuable for testing. Adopt **both**.

### E.5 progressToken + HTML auto-spill

Plan A: opt-in `progressToken`; HTML threshold env `REV_SPIDER_HTML_INLINE_MAX_BYTES=262144`; `content_trust: "untrusted"`. Plan B: all long tools progress; cancellation via `notifications/cancelled`.

**統合判断:** Plan B's "all long tools support progress" wins (consistency; matches MCP best practice). Adopt Plan A's HTML auto-spill threshold (256 KiB) verbatim. Adopt Plan B's cancellation contract (SIGTERM grace then SIGKILL) — Plan A omits cancellation entirely; this is a real gap.

### E.6 session_id / session_show

Plan A only. Plan B does not mention session correlation explicitly. **統合判断: Adopt Plan A in full** — session correlation is the foundation for `correlation_id` (already in our ErrorEnvelope), and the absence of a `session_show` MCP tool would force agents to grep journald. Worth the 1 day.

### E.7 `--log-json` + `tool_latency_ms`

Both plans agree (Plan B adds `LogFormat::Journald` variant). **統合判断:** Adopt union — `human`/`json`/`journald` log formats; `tool_latency_ms` + `started_at_iso` in every `structuredContent`.

## F. クレート構成変更

**Plan A:** **Zero new mandatory crates.** All work as new modules within `stealth-cli` / `stealth-mcp` / `stealth-core` / `stealth-auth`. Rationale: minimises workspace churn and Cargo build-graph rebalancing.

**Plan B:** **Two new crates:**
- `stealth-config` — paths, schema, validation, migration, writer.
- `stealth-agent-contracts` — MCP schemas, error envelope, rate-limit config, progress types.

Rationale: shared by `stealth-cli` (for `config` subcommand) and `stealth-mcp` (for config tools and tool definitions). Avoids cyclic dep on `stealth-cli`.

**統合判断: Plan B wins, but only the contracts crate.**

- **`stealth-agent-contracts` (new crate): YES.** The `ErrorEnvelope`, `ErrorCode`, `ToolRateLimit`, `ProgressNotification` types are genuinely shared between `stealth-mcp` and `stealth-cli` (exit-code mapping reads `ErrorCode`). Putting them in `stealth-cli` would force `stealth-mcp` to depend on the CLI crate — wrong dependency direction. Plan A's "module in stealth-mcp" makes `stealth-cli` depend on `stealth-mcp` — also wrong. **New crate is the right answer.**
- **`stealth-config` (new crate): NO** — defer to v1.3. Plan B is right that `ConfigWriter` is shared between `stealth-cli` (CLI writes) and `stealth-mcp` (MCP `policy_apply_change` writes), but the volume of code is small enough to live in `stealth-cli` and be re-exported. New crate is workspace overhead without payoff in v1.2.0. **Plan A wins here.**

Final crate delta: **+1 crate** (`stealth-agent-contracts`), 0 crates removed.

> **Debate trace (crate count):**
> - Plan A: +0 crates.
> - Plan B: +2 crates.
> - **統合判断: +1 crate** (agent-contracts only). Config layer ships as `stealth-cli::config_io` module, re-exported for MCP server use.

## U. 議論ハイライト — 7 most consequential conflicts

| # | Chapter | Plan A 主張 | Plan B 主張 | 統合判断 | 技術根拠 |
|---|---------|-------------|-------------|----------|----------|
| 1 | E.1 outputSchema source | hand-written JSON files (`include_str!`) | `schemars`-derived from Rust types | **Plan A** | OpenAI Agent SDK strict-mode rejects fields `schemars` happily emits (e.g. `nullable`); `format`, `examples`, per-field `description` belong in the agent contract, not in `#[schemars(...)]` attrs. JSON is the canonical agent surface; Rust is the implementation. Inverting the relationship couples lifecycle (every Rust struct edit churns the agent contract). |
| 2 | B.3 systemd `Accept=` | `yes` (per-connection) | `no` (single long-lived process) | **Plan B** | Stdio JSON-RPC for MCP carries session state: token-bucket counters, `session_id` correlation, recipe cache hits. `Accept=yes` forks per TCP connection — every fork loses that state. Per-connection forking is correct for stateless protocols (echo, HTTP/1.0); wrong for stateful JSON-RPC over stdio. |
| 3 | D.2 `schema_version` initial value | `=1` (reserved; no migration shipped) | `=2` (jump + ship migration) | **Plan A** | No breaking schema change exists in v1.2.0. Bumping to `2` forces every operator to run `migrate` for a no-op cosmetic change. Reserve `=1` now; first real migration becomes `1→2` in v1.3 when the change is justified. Semantic version bumps without semantic changes erode trust in the migration system. |
| 4 | F. crate layout | `+0` crates (modules only) | `+2` crates (`stealth-config` + `stealth-agent-contracts`) | **+1 (contracts only)** | `ErrorEnvelope`/`ErrorCode` are shared between `stealth-cli` (exit-code mapping) and `stealth-mcp` (JSON-RPC error.data). Putting them in either crate forces the other to depend on it — wrong dep direction. New crate is the only acyclic solution. Config layer is small enough (~400 LOC) to live in `stealth-cli` and be re-exported; new crate would be ceremony without payoff. |
| 5 | E.2 ErrorEnvelope shape | `kind` field, `hint` optional | `code` field, `hint` required | **Plan B** | `code` is the cross-API convention (Anthropic, OpenAI, Stripe, AWS). `hint` required forces every error site to produce one actionable sentence — without that discipline, half of envelopes ship with `hint=None` and agents recover poorly. Mandatory string is cheap; ergonomic dividend is large. |
| 6 | B.4 systemd credentials | native read of `$CREDENTIALS_DIRECTORY/auth-pass` (rev-auth source change) | env-var pointing to file path via `LoadCredentialEncrypted=...` + `Environment=..._FILE=%d/...` | **Plan B** | Canonical systemd ≥ 252 idiom. Plan A's "native read" exposes passphrase content nowhere — but it requires rev-auth to learn about `$CREDENTIALS_DIRECTORY`, which couples auth code to systemd's runtime contract. Plan B's `..._FILE` approach reuses the existing env-var convention (`stealth-auth` already supports `_FILE` patterns idiomatically); passphrase content is never in env (only the file path is). Same security floor, zero coupling. |
| 7 | D.2 `deny_unknown_fields` rollout | hard from v1.2.0 + env LENIENT, removed v1.3 | hard for new parser + `--compat-v1`, kept indefinitely | **hybrid** | Hard rollout catches typos (the point of the change). But Plan A's env-only escape is invisible in audit logs; Plan B's per-invocation `--compat-v1` is auditable but doesn't help systemd units where env is the only injection path. Ship **both** mechanisms; remove in **v1.4** (Plan A said v1.3 — give operators an extra release of grace). |
